🌐 1. Nguyên Lý Bắt Tay ETag (304 Not Modified)

ETag giống như một "dấu niêm phong" trên phong bì. Khi client nhận dữ liệu lần đầu, nó ghi nhớ dấu niêm phong này. Lần sau cần lấy dữ liệu, nó chỉ hỏi: "Niêm phong có đổi không?". Nếu không đổi, server chỉ bảo "Chưa đổi đâu!" (304), khỏi cần gửi lại cả phong bì 25MB!

⚖️ 2. Đặt Lên Bàn Cân: Option A vs Option B

Tại sao bố m hỏi m trước khi làm? Vì mỗi phương án đều có ưu và nhược điểm đối với ứng dụng nghe nhạc:

Cân nhắc kiến trúc YAGNI & Ponytail
Option A: HTTP ETag Caching KHUYÊN DÙNG

Giữ nguyên việc load toàn bộ khi mở app, nhưng chặn đứng 100% việc tải thừa qua mã 304.

  • Ưu điểm: Giữ nguyên tính năng Shuffle toàn cục (ngẫu nhiên toàn thư viện) và Instant Search gõ phím tìm kiếm tức thì đéo cần mạng.
  • Độ phức tạp: Cực thấp, chỉ sửa ~30 dòng code server và client, đéo làm vỡ giao diện.
  • Nhược điểm: Lần đầu mở app nếu thư viện có > 50.000 bài thì tải lần đầu vẫn hơi nặng.
Option B: Cursor Pagination ENTERPRISE SCALE

Chỉ tải 50 bài một lần, cuộn chuột đến đâu gọi API kéo tiếp đến đó (Infinite Scroll).

  • Ưu điểm: Dù thư viện có 1.000.000 bài thì RAM vẫn chỉ ăn vài MB, khởi động dưới 50ms.
  • Nhược điểm: Phải viết lại thanh Search (tìm kiếm phải gửi lên server query SQLite), và nút Shuffle ngẫu nhiên phải sinh hàng đợi từ server.
  • Độ phức tạp: Cao, chạm vào hàng chục file store Zustand và component.
